# 03.10 Verification & Acceptance

> **Baseline v1.** Verification may be AI-heavy and highly automated, but acceptance of meaning, residual risk and business correctness remains human-owned.

## 1. Intent

### Purpose

The purpose of **Verification & Acceptance** is to establish sufficient independent evidence that the reviewed implementation satisfies the approved functional and non-functional correctness contract and is acceptable for release.

Verification answers **“does the implementation satisfy the defined contract?”**. Acceptance answers **“is the evidence sufficient to authorize release?”**.

### Scope

**IN SCOPE**

* functional validation,
* manual acceptance where appropriate,
* exploratory testing,
* selected automated E2E,
* integration/API/contract validation where required,
* relevant NFR validation,
* regression evidence,
* evaluation of residual defects and risks,
* explicit acceptance decision.

**OUT OF SCOPE**

* implementation design,
* code review already covered by 03.09,
* production deployment,
* production smoke and observation,
* tool-specific automation conventions.

### Inputs

Verification & Acceptance SHOULD consume:

* PR-approved / reviewed implementation,
* approved Test Intent / scenario set,
* acceptance criteria,
* relevant NFR expectations,
* automated test results already produced,
* known defects/deviations,
* current risk classification.

### Entry Criteria

The stage MAY start when:

* the implementation has passed required Review controls,
* the tested artifact/change is identifiable,
* the correctness contract is current,
* required environments/test data are available or limitations are explicit,
* no known blocking implementation defect prevents meaningful validation.

## 2. Responsibility & Authority

### Human Responsibilities

Humans MUST:

* validate that test evidence corresponds to intended behavior,
* perform or own manual/exploratory validation where required,
* approve business-critical expected outcomes,
* decide whether residual defects or limitations are acceptable,
* approve changes to acceptance criteria or test oracles,
* make the final Acceptance Passed decision through an authorized role.

### AI Responsibilities / Permitted Role

AI MAY:

* generate detailed manual test scripts from approved scenarios,
* implement and execute selected E2E tests,
* prepare exploratory charters,
* execute and analyze regression suites,
* aggregate test evidence,
* correlate failures across layers,
* propose missing regression scenarios,
* summarize residual risk and failed validation areas.

AI MUST NOT:

* change expected results to make a failing test pass,
* declare business acceptance without human authorization,
* treat E2E as a mandatory 1:1 copy of manual tests,
* suppress flaky or failed evidence without visibility.

### Decision Rights

| Material Decision | Human Authority |
| --- | --- |
| Acceptance of business behavior | Product / Business / QA as applicable |
| Acceptance of residual defect | Product / QA / Lead / Risk Owner |
| NFR acceptance | Relevant Lead / Security / Operations / Business authority |
| Correctness-contract change | Appropriate Human Owner |
| Waiver of a required validation layer | Authorized Risk / Delivery Owner through exception process |
| Acceptance Passed | Designated QA / Product / Team authority |

## 3. Execution Contract

### Logical Activities

**Confirm Validation Scope → Execute Functional / Integration Evidence → Perform Manual & Exploratory Validation → Execute Selected E2E → Execute Relevant NFR Validation → Run Required Regression → Aggregate Results → Assess Residual Risk → Human Acceptance Decision**

Validation layers MAY execute in parallel. AI-SDLC does not require a strictly sequential test pipeline.

### Required Artifacts

At exit, logical artifacts SHOULD include, as applicable:

* **Functional Test Results**,
* **Manual / Exploratory Evidence**,
* **Selected E2E Results**,
* **NFR Validation Results**,
* **Regression Evidence**,
* **Acceptance Record**,
* **Residual Risk / Known Defect Record**.

### Mandatory Validation Principles

* E2E SHOULD protect critical end-to-end journeys, representative happy paths, important integration paths and selected high-value failure scenarios.
* E2E MUST NOT automatically duplicate every manual scenario.
* Lower-level unit/component/integration/contract/API testing SHOULD be preferred where it provides faster and more reliable evidence.
* Manual and exploratory testing remain valid engineering evidence and SHOULD be used where human judgment provides value.
* NFR validation MUST be included when security, performance, resilience, concurrency, recoverability, observability or compatibility is material to the change.
* The same AI that implemented the change MUST NOT be the sole source of confidence for material acceptance.

## 4. Control

### Primary Gate — Acceptance Passed

The change is accepted for release when required functional and non-functional validation has produced sufficient evidence and the authorized human owner accepts the remaining risk.

### Exit Criteria

The gate MUST confirm, proportionally to risk, that:

* critical functional scenarios pass,
* required negative/failure scenarios pass or have accepted deviations,
* selected E2E evidence is green or known limitations are accepted,
* required manual/exploratory validation is complete,
* relevant NFR expectations are validated,
* regression evidence is sufficient,
* failed/flaky tests are visible rather than silently ignored,
* residual defects/risks have owners and explicit decisions,
* the correctness contract has not been silently changed,
* authorized humans approve release readiness from a validation perspective.

### Required Evidence

Evidence SHOULD include:

* test execution records,
* manual/exploratory findings,
* NFR results,
* acceptance identity/decision,
* explicit defect/risk waivers where applicable.

### Risk Adjustments R0–R4

* **R0:** MAY rely on focused automated validation and lightweight human acceptance.
* **R1:** SHOULD use standard functional/regression validation and selected manual/E2E evidence.
* **R2:** MUST use multiple appropriate validation layers and SHOULD include exploratory/NFR evidence where material.
* **R3:** MUST use stronger independent validation, explicit NFR/security/performance checks as relevant and human acceptance of residual risk.
* **R4:** MUST use auditable, independent and specialist validation, explicit acceptance authority and tightly controlled exceptions.

### Stop / Escalation Conditions

Escalate when:

* critical validation fails,
* implementation and accepted expected behavior conflict,
* a test oracle appears incorrect but has not been human-approved for change,
* required NFR evidence cannot be produced,
* environment/test-data limitations make evidence unreliable,
* risk increases materially,
* residual defects exceed accepted thresholds.

### Exceptions

Validation MAY be reduced through the approved exception process when urgency or environment constraints justify it. Compensating controls SHOULD be introduced, such as narrower rollout, stronger observation, feature flags or additional human review. Deferred validation MUST remain visible and owned.
