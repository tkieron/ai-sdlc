# 03.11 Release & Deployment

> **Baseline v1.** Release & Deployment promotes a trusted, accepted artifact through controlled environments into production and does not complete until production behavior is verified.

## 1. Intent

### Purpose

The purpose of **Release & Deployment** is to safely promote the accepted software artifact into production using risk-appropriate controls, explicit recoverability, production smoke validation and post-deployment observation.

AI-SDLC follows the principle:

> **Done = deployed, verified and operating correctly in production.**

### Scope

**IN SCOPE**

* merge/integration of the approved change,
* build-once / immutable-artifact creation,
* artifact promotion through environments,
* deployment configuration and migration readiness,
* Ready for Production gate,
* deployment strategy,
* recovery / rollback / roll-forward strategy,
* production deployment,
* smoke validation,
* post-deployment observation,
* explicit Release Accepted decision.

**OUT OF SCOPE**

* development/review of source changes,
* functional acceptance already covered by 03.10,
* long-term incident/problem management after release acceptance,
* tool-specific deployment commands and pipeline implementation.

### Inputs

Release & Deployment SHOULD consume:

* PR-approved and Acceptance-Passed change,
* identifiable trusted source state,
* approved release candidate scope,
* current risk classification,
* migration/configuration requirements,
* observability expectations,
* known residual risks,
* required deployment/recovery constraints.

### Entry Criteria

The stage MAY begin when:

* required Review and Acceptance gates are complete,
* the release scope is identifiable,
* the release artifact can be built reproducibly or otherwise uniquely identified,
* residual defects/risks are known,
* release ownership is assigned.

## 2. Responsibility & Authority

### Human Responsibilities

Humans MUST:

* own the production release decision,
* ensure release risk is understood,
* approve or own deployment strategy for material releases,
* define/approve a credible recovery strategy,
* approve material migration/data-risk decisions,
* decide GO / NO-GO where explicit human approval is required,
* decide rollback/roll-forward/abort actions when thresholds are crossed,
* accept the release only after required smoke and observation evidence.

### AI Responsibilities / Permitted Role

AI MAY:

* analyze pipeline/deployment failures,
* compare environment configuration and release metadata,
* generate release summaries and checklists,
* monitor and correlate telemetry during rollout,
* recommend GO/NO-GO, abort, rollback or roll-forward,
* execute pre-authorized bounded automation,
* summarize production observation evidence.

AI MUST NOT:

* obtain unrestricted production authority by default,
* invent a recovery strategy after failure where one was required beforehand,
* override hard security/compliance controls,
* declare a material release accepted without authorized human/policy approval.

### Decision Rights

| Material Decision | Human Authority |
| --- | --- |
| Release scope | Product / Delivery / Release Owner |
| Deployment strategy | Release Owner / Platform / Lead |
| Migration / irreversible data decision | Lead / Architect / Data Owner |
| Ready for Production | Authorized Release / Risk Owner |
| GO / NO-GO | Release Owner / designated authority |
| Abort / rollback / roll-forward | Release Owner / Incident authority according to policy |
| Release Accepted | Release Owner / Business/Operations authority as applicable |

## 3. Execution Contract

### Logical Activities

**Merge Approved Change → Build Once → Create/Identify Immutable Artifact → Promote to INT/QA/PREPROD as applicable → Validate Deployment/Migrations → Prepare Release Safeguards → Ready for Production → Deploy / Progressive Rollout → Production Smoke → Observation Window → Release Accepted**

The same trusted artifact SHOULD be promoted through environments where technically feasible.

### Required Artifacts

At exit, logical artifacts SHOULD include:

* **Trusted / Immutable Artifact Identifier**,
* **Release Package / Release Scope**,
* **Deployment Strategy** where material,
* **Recovery Strategy**,
* **Migration / Data Change Plan** where applicable,
* **Release Gate Evidence**,
* **Production Smoke Results**,
* **Observation Evidence**,
* **Release Acceptance Record**.

### Mandatory Artifact Content

#### Recovery Strategy

Every material release MUST have a credible recovery strategy defining, where applicable:

* relevant failure modes,
* detection signals / triggers,
* abort conditions,
* feature-disable option,
* application/configuration rollback option,
* roll-forward option,
* data/migration recovery implications,
* decision owner,
* expected response time or escalation path.

**Recovery capability is mandatory for material releases. Rollback capability is context-dependent.**

#### Release Gate

Ready for Production MUST verify, proportionally to risk:

* correct artifact identity,
* required CI / acceptance evidence,
* configuration/secrets readiness,
* migration readiness,
* observability readiness,
* deployment strategy,
* recovery strategy,
* accepted residual risk,
* accountable release owner.

### Deployment & Migration Principles

* Prefer **build once → verify → promote**.
* Prefer compatibility-oriented migration such as **expand → migrate → observe → contract** where appropriate.
* Deployment MAY use rolling, blue/green, canary, progressive rollout and feature flags according to risk.
* Feature activation MAY be separated from code deployment.
* Higher risk SHOULD reduce blast radius and increase observation checkpoints.

## 4. Control

### Gate 1 — Ready for Production

The release candidate may enter production only when required release safeguards are ready and residual risk has been accepted by the appropriate authority.

### Gate 2 — Release Accepted

The release is complete only after production smoke and observation provide sufficient evidence that the deployed change operates correctly.

### Exit Criteria

Release Accepted MUST confirm, proportionally to risk, that:

* deployment completed successfully,
* critical smoke tests passed,
* no unacceptable technical degradation is observed,
* relevant business KPIs remain acceptable,
* migrations/data changes are stable,
* recovery has not been required or has completed successfully,
* unresolved production signals have owners,
* authorized humans/policies accept the release.

### Required Evidence

Evidence SHOULD include:

* artifact/release identity,
* promotion/deployment records,
* release gate decision,
* smoke results,
* technical/business telemetry,
* recovery/rollback evidence if invoked,
* Release Accepted record.

### Risk Adjustments R0–R4

* **R0:** MAY use mostly automated release gates and standard rollback capability.
* **R1:** SHOULD use standard promotion, smoke and defined recovery.
* **R2:** MUST define explicit recovery and relevant observation; feature flags/progressive rollout SHOULD be considered.
* **R3:** MUST use controlled rollout, explicit Ready for Production approval, stronger observation and recovery that is tested where practical.
* **R4:** MUST use highly controlled deployment, explicit multi-party/specialist approval as applicable, demonstrated recoverability where feasible, and tightly bounded AI production authority.

### Stop / Escalation Conditions

Deployment/rollout MUST stop or escalate when:

* required release evidence is missing,
* migration safety is uncertain,
* recovery strategy is not credible,
* smoke fails critically,
* error/latency/business KPI thresholds are crossed,
* data-integrity/security signals appear,
* risk increases materially during rollout,
* AI proposes an unauthorized production action.

### Exceptions

Emergency release MAY use a break-glass path. It MUST preserve:

* explicit accountable owner,
* minimum safe validation,
* visible exception decision,
* credible recovery path,
* heightened post-deployment observation,
* post-action review for material incidents.

## 5. Traceability & Navigation

### Traceability

**Acceptance Evidence → Release Candidate → Trusted Artifact → Ready for Production → Deployment → Smoke / Observation → Release Accepted → Production Feedback**
