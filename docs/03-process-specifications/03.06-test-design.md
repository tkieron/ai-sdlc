# 03.06 Test Design

> **Baseline v1.** Test Design defines the correctness contract before implementation mechanics. Humans own test intent; AI may support scenario discovery and later test implementation.

## 1. Intent

### Purpose

The purpose of **Test Design** is to define how the team will recognize that the planned change is correct, safe and acceptable before implementation begins.

Test Design establishes the logical **correctness contract**: what must be verified, why it matters, which scenarios are critical and which validation layers are appropriate.

### Scope

**IN SCOPE**

* test intent,
* critical functional scenarios,
* main happy and negative paths,
* business-rule validation,
* boundary and failure scenarios,
* permissions / role scenarios,
* integration failure modes,
* relevant NFR validation expectations,
* selection of appropriate validation layers,
* identification of manual/exploratory and E2E candidates,
* traceability between requirements and validation.

**OUT OF SCOPE**

* final implementation of test code,
* framework-specific test conventions,
* selector/page-object implementation,
* full regression-suite maintenance procedures,
* detailed CI orchestration.

### Inputs

Test Design SHOULD consume:

* approved Functional Specification,
* acceptance criteria,
* approved Architecture Design / material contracts,
* planned work and Definition of Done,
* known risks and dependencies,
* current R0–R4 classification,
* relevant historical defects or production evidence where available.

### Entry Criteria

Test Design MAY start when:

* intended behavior is sufficiently understood,
* acceptance criteria are available,
* material architecture constraints affecting validation are known,
* the team can identify critical user/business paths and risk-relevant failure modes.

## 2. Responsibility & Authority

### Human Responsibilities

Humans MUST:

* define the intent of validation,
* approve what constitutes expected behavior,
* identify critical scenarios,
* decide which NFRs require explicit validation,
* approve changes to the accepted correctness contract,
* decide which scenarios warrant E2E versus lower-level testing,
* confirm that the test strategy is proportionate to risk.

### AI Responsibilities / Permitted Role

AI MAY:

* propose additional scenarios and edge cases,
* map requirements to candidate tests,
* identify gaps in scenario coverage,
* propose negative and failure paths,
* suggest which validation layer best fits a scenario,
* draft manual test cases and exploratory charters,
* draft test-code skeletons after test intent is approved,
* analyze historical defect patterns to suggest regression coverage.

AI MUST NOT:

* redefine expected behavior to make implementation easier,
* change an accepted test oracle without human approval,
* treat generated tests as proof that the specification is complete,
* convert every manual scenario into E2E by default.

### Decision Rights

| Material Decision | Human Authority |
| --- | --- |
| Expected result / test oracle | Product / Analyst / QA / Domain Owner as appropriate |
| Critical scenario classification | QA / Team / Product |
| NFR validation requirement | Lead / Architect / QA / Security / Operations |
| E2E selection | QA / Team / Lead |
| Correctness-contract change | Appropriate Human Owner |
| Test Design approval | QA / Team / Lead according to local governance |

## 3. Execution Contract

### Logical Activities

**Review Requirements & DoD → Identify Critical Behaviors → Define Happy / Negative / Boundary / Failure Scenarios → Identify NFR Validation → Choose Appropriate Test Layers → Select Manual / Exploratory / E2E Candidates → Check Traceability & Coverage → Human Approval → Correctness Contract Ready**

### Required Artifacts

At exit, logical artifacts MUST include:

* **Test Intent / Validation Strategy**,
* **Approved Scenario Set**,
* **Requirement ↔ Validation Traceability**.

Where applicable, Test Design SHOULD also produce:

* manual-test candidates,
* exploratory-testing charter,
* E2E candidate list,
* NFR validation plan,
* test-data needs,
* known limitations or residual validation risk.

### Mandatory Artifact Content

The Test Intent MUST define, where applicable:

* what is being validated,
* why it matters,
* expected behavior,
* critical scenarios,
* important negative/boundary/failure scenarios,
* selected validation layer or rationale,
* relevant NFR expectations,
* known assumptions or untestable areas,
* ownership of material validation decisions.

Before implementation:

* **all critical scenarios MUST be known**, and
* as a working baseline, teams SHOULD aim to identify the substantial majority of meaningful functional scenarios in advance (approximately **70–85%** for typical feature work), while accepting that implementation and exploratory work will reveal additional cases.

Detailed manual steps and complete regression automation do not need to exist before development.

### Correctness Contract Rule

Once material test intent / expected outcomes are human-approved, AI MUST NOT unilaterally change them to make its implementation pass.

A mismatch MUST be treated as:

**STOP → REPORT MISMATCH → PROPOSE OPTIONS → HUMAN DECISION**

The contract MAY change when new information appears, but the change requires explicit human acceptance.

## 4. Control

### Local Gate — Test Intent Approved / Correctness Contract Ready

Test Design is complete when the team can explain **how the change will be recognized as correct** and when the critical validation intent is sufficiently stable to constrain implementation.

### Exit Criteria

The gate MUST confirm, proportionally to risk, that:

* critical scenarios are defined,
* expected outcomes are explicit,
* main functional and important negative paths are covered,
* relevant permission/integration failure cases are visible,
* material NFR validation is identified,
* E2E is selective rather than a 1:1 copy of manual testing,
* traceability to requirements exists,
* residual gaps are explicit,
* humans approve the correctness contract.

### Required Evidence

Evidence SHOULD include:

* approved Test Intent / Scenario Set,
* traceability evidence,
* explicit NFR validation decisions,
* human approval of material expected outcomes.

### Risk Adjustments R0–R4

* **R0:** MAY use lightweight test intent and existing regression coverage.
* **R1:** SHOULD define standard functional scenarios and appropriate automated validation.
* **R2:** SHOULD include explicit negative paths, integration failures and selected NFR coverage.
* **R3:** MUST use multi-layer validation, stronger independence of evidence and explicit specialist NFR/security testing where relevant.
* **R4:** MUST define auditable critical scenarios, independent validation and explicit acceptance authorities; test intent MUST NOT depend solely on the implementing AI.

### Stop / Escalation Conditions

Escalate when:

* expected behavior is ambiguous,
* requirement and architecture imply incompatible outcomes,
* a critical scenario cannot be tested or observed,
* risk class increases materially,
* AI proposes changing expected behavior to satisfy implementation,
* required NFR evidence cannot be produced,
* the same AI would become the sole author and sole validator of a material artifact.

### Exceptions

Emergency work MAY reduce scenario breadth, but critical safety/business behavior and rollback/recovery validation MUST remain explicit where production is affected. Deferred validation MUST be visible and owned.

## 5. Traceability & Navigation

### Traceability

**Requirement → Acceptance Criterion → Test Intent / Scenario → Validation Evidence**

Where E2E is selected:

**Requirement → Manual/Business Scenario → Selected Automated E2E**
