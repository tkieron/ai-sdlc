# 03.07 Implementation Design

> **Baseline v1.** Implementation Design is human-owned and prepares a bounded, AI-ready execution contract without forcing humans to specify every mechanical implementation detail.

## 1. Intent

### Purpose

The purpose of **Implementation Design** is to transform approved functional, architectural, planning and correctness intent into a sufficiently explicit implementation model that a developer and, where permitted, an AI agent can execute without inventing material design decisions.

The stage defines **WHAT must be implemented, the key constraints, and the important HOW**, while leaving local and reversible implementation detail to execution.

### Scope

**IN SCOPE**

* domain model and invariants,
* DTO / contract expectations,
* public interfaces and component responsibilities,
* data and control flow,
* component communication,
* transaction boundaries,
* material concurrency behavior,
* persistence implications,
* important failure and error behavior,
* key concrete classes/components where needed,
* public-method pseudocode or algorithm intent where useful,
* allowed and forbidden change scope,
* AI implementation contract,
* mapping of approved tests/DoD to implementation constraints.

**OUT OF SCOPE**

* exhaustive design of every private helper,
* line-by-line pseudocode,
* formatting or boilerplate details,
* implementation work itself,
* autonomous redefinition of architecture or correctness.

### Inputs

Implementation Design SHOULD consume:

* approved Functional Specification,
* Architecture Design and material ADRs,
* refined requirements,
* approved work plan / DoD,
* approved Test Intent / Correctness Contract,
* current risk classification,
* applicable project standards and existing codebase constraints.

### Entry Criteria

Implementation Design MAY start when:

* material requirements and architecture are approved,
* planned work boundaries are known,
* test intent is sufficiently defined,
* no unresolved Material Decision blocks implementation,
* the responsible developer/lead has sufficient context to own the resulting design.

## 2. Responsibility & Authority

### Human Responsibilities

Humans MUST:

* own the implementation intent,
* define/approve domain model and invariants,
* define/approve public contracts and interfaces,
* define/approve transaction, consistency and key concurrency boundaries,
* decide important component responsibilities and data flow,
* define allowed and forbidden scope for delegated execution,
* approve the AI Implementation Contract where AI execution is used,
* ensure the design remains consistent with architecture and correctness intent.

### AI Responsibilities / Permitted Role

AI MAY:

* analyze the existing codebase to identify affected components,
* challenge design completeness,
* propose local class/helper structures,
* identify missing error/failure paths,
* draft pseudocode or sequence diagrams,
* propose mechanical mappings and boilerplate structures,
* prepare a draft AI Implementation Contract from approved design,
* check consistency between implementation design, tests and architecture.

AI MUST NOT:

* silently introduce new Material Decisions,
* redefine domain invariants or public contracts,
* expand implementation scope without authorization,
* replace human ownership with a generic “implement the ticket” plan.

### Decision Rights

| Material Decision | Human Authority |
| --- | --- |
| Domain model / invariants | Developer / Tech Lead / Domain Owner |
| Public interface / contract | Developer / Lead / Architect |
| Transaction / consistency boundary | Lead / Architect / Developer with authority |
| Material concurrency strategy | Lead / Architect |
| Allowed implementation scope | Human Owner / Lead |
| Deviation from architecture | Architect / Lead through explicit decision |
| Readiness for implementation | Developer / Tech Lead / Team as applicable |

## 3. Execution Contract

### Logical Activities

**Review Approved Inputs → Model Domain & Invariants → Define Contracts / Interfaces → Define Data & Control Flow → Define Transaction / Failure Boundaries → Identify Affected Components → Define Allowed / Forbidden Scope → Map Correctness Contract → Draft AI Implementation Contract → Human Review → Ready for Development**

### Required Artifacts

At exit, the following logical artifacts MUST exist for material AI-assisted implementation:

* **Implementation Design**,
* **AI Implementation Contract / Bounded Work Package**,
* references to the **Approved Correctness Contract**.

For low-risk or fully human implementation, the AI Implementation Contract MAY be simplified or omitted if the implementation intent is already sufficiently explicit.

### Mandatory Artifact Content

#### Implementation Design

MUST define, where applicable:

* objective and affected area,
* domain model and invariants,
* public/internal contracts,
* component responsibilities,
* data/control flow,
* transaction/consistency boundaries,
* important concurrency behavior,
* persistence implications,
* error/failure behavior,
* key implementation decisions,
* important pseudocode/algorithm intent where useful,
* architectural constraints and references.

#### AI Implementation Contract

MUST define, proportionally to risk:

* **Goal**,
* **Input context**,
* **Allowed changes / scope**,
* **Forbidden changes / protected areas**,
* **Contracts and invariants**,
* **Approved tests / correctness expectations**,
* **Definition of Done**,
* **Required validations**,
* **Material decisions already made**,
* **Stop / escalation conditions**,
* **Known unresolved questions** — ideally none that block execution.

The contract SHOULD be concise enough to execute yet explicit enough to prevent autonomous scope expansion.

## 4. Control

### Primary Gate — Ready for Development

Implementation Design is complete when the team knows what must be built, how correctness will be recognized, which material design decisions are fixed and what autonomy may be delegated during execution.

### Exit Criteria

The gate MUST confirm, proportionally to risk, that:

* requirements and architecture are sufficiently stable,
* critical test intent / expected behavior is approved,
* domain/contracts/invariants are explicit where material,
* important transaction/failure boundaries are defined,
* implementation scope is bounded,
* Material Decisions are human-owned and resolved,
* AI stop/escalation conditions are known where relevant,
* no blocking open question requires the agent to invent product or architecture intent,
* the responsible developer/lead understands and approves the implementation model.

### Required Evidence

Evidence SHOULD include:

* approved Implementation Design,
* approved AI Implementation Contract where applicable,
* references to approved test intent/DoD,
* human approval of Ready for Development.

### Risk Adjustments R0–R4

* **R0:** MAY use a lightweight implementation note or direct local execution under existing patterns.
* **R1:** SHOULD define scope, contracts and DoD clearly; local HOW may remain with AI.
* **R2:** MUST use explicit boundaries, important invariants, failure behavior and implementation contract for delegated work.
* **R3:** MUST tightly constrain agent scope, explicitly document transaction/security/data implications and require lead approval.
* **R4:** MUST be human-first, use strongly bounded AI support only, preserve explicit specialist decisions and avoid delegating critical design authority.

### Stop / Escalation Conditions

Escalate when:

* implementation requires changing public contracts, architecture or schema outside approved scope,
* a new dependency or security permission is required,
* correctness criteria conflict with architecture or codebase reality,
* risk class increases materially,
* the implementation cannot be bounded without unresolved Material Decisions,
* AI would need to modify protected areas to complete the task.

Use **STOP → DESCRIBE → PROPOSE → ESCALATE**.

### Exceptions

Low-risk work MAY omit formal design artifacts when existing conventions fully determine the solution and the Human Owner still understands the intended change. Simplification MUST NOT be used to bypass material decision ownership.
